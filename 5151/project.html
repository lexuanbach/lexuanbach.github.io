Group Project · CO5151 · 50% of the final grade

Design, build, and evaluate one agentic AI system

Each group of 3–4 designs, implements, and evaluates a complete agentic AI system for a real problem — proposed in Week 2, checkpointed in Week 7, and defended across two rounds in Weeks 12–13. The topic itself must be novel, non-trivial, meaningful, and feasible in ~10 weeks; the system must apply at least three of the advanced axes covered in the seminars, and both a quantitative evaluation and a security analysis are mandatory.

01 · Minimum technical requirements

What every system must have

Topic-quality gate — checked at D1, before R1–R9 apply

R1–R9 below specify what the system must contain. These four criteria gate what topic is acceptable in the first place — a proposal that satisfies every R below on paper but fails one of these still comes back "changes required."

Novel

Not a reproduction

Not a direct copy of an existing tutorial, course example, or published demo — at least one element (task, axis combination, evaluation, or deployment context) is your own choice.

Non-trivial

Can't be vibe-coded in a day

Requires genuine design decisions — real integration across ≥ 3 advanced axes, real failure handling, and an evaluation that surfaces a non-obvious trade-off.

Meaningful

Has real value

Either a research contribution (tests a hypothesis, yields a reusable artifact or finding) or a practical application solving an actual problem — not a "hello world" agent with no audience.

Feasible

Fits ~10 weeks

Achievable by your 3–4 person team between the D1 proposal (Week 2) and Round 1 (Week 12), given your stated skills and compute/API budget — your work plan must show this.

R1
D1 · D2 · D3

Clear agent architecture

Reasoning–acting loop and/or planning and/or multi-agent orchestration, documented as a diagram plus a state/control-flow description.

R2
D2 · D3

Tools / MCP integration

At least one MCP server (your own or third-party) or an equivalent function-calling toolset, with tool permissions documented.

R3
D2 · D3

Memory

An explicit design — short-term/context management plus at least one long-term or episodic store — with a stated write/retrieve policy.

R4
D1 · D3

≥ 3 advanced axes

Beyond tools and memory: e.g., planning/search, reflection/verification, multi-agent, RAG, RL fine-tuning, computer use, or guardrails. Depth beats breadth.

R5
D2 · D3

Quantitative evaluation

A benchmark or curated task set (≥ 20 tasks), a success metric, cost and latency, ≥ 2 system configurations (ablation), ≥ 3 runs/seeds with variance, and an error analysis.

R6
D1 · D3

Security & safety analysis

A threat model (assets, entry points, attacker capabilities); tests for direct + indirect prompt injection (≥ 10 attack cases); permission control / least privilege on tools; monitoring & audit logging.

R7
W7 · W12 · W13

Demo

A live demo backed by a recorded video — network or API outages must not stop your defense.

R8
D4

Reproducible code

README, pinned dependencies, .env.example, a one-command run, evaluation scripts, seeds, traces/logs, and a cost report.

R9
D3

Report

6–8 pages, conference style, with an AI-use statement and a contribution statement.

02 · Deliverables

Milestones and deadlines

before W2

Idea 1-pager (formative)

Problem, users, why an agent (vs. a script or single prompt), and candidate advanced axes.

due Sun 13 Sep · pitch W2

D1 — Proposal (3–4 pp.) + 5′ pitch 20% of PRJ

Architecture sketch, tools/MCP + memory design, ≥ 3 axes, evaluation plan, a v0 threat model, work plan and risks. Verdict: approved / changes required / resubmit. If the proposal is still unapproved in Week 3, one point is deducted from the architecture criterion.

due Sun 25 Oct · checkpoint W7

D2 — Interim progress report (4–6 pp.) + 8′ live demo 30% of PRJ

Implemented architecture, first evaluation numbers (even on 5–10 tasks), threat model v1 with first injection tests, and a revised plan to W12. Status recorded as on track / at risk / re-scope.

due Sun 29 Nov · defense W12

D3 v1 + D4 — Final report v1 + code, tagged v1 50% of PRJ, split below

Round 1 defense: 10′ presentation with live demo + 5′ Q&A, reviewed by a peer group and the instructor.

W13 · Wed 9 Dec

Round 2 defense + final submission

Defend what changed since Round 1 and why, along with final results, limitations, and extensibility. Submit D3 v2, the contribution statements, the intra-group peer evaluation, and D4 tagged final by Fri 11 Dec, 23:59, after incorporating any final defense feedback.

Weighting inside the project component (PRJ, 50% of the course): Proposal (D1) 20% · Interim progress report (D2) 30% · Final report + code + presentation (D3/D4, both defense rounds) 50% — of that final 50%: report 30/50, reproducible code 10/50, presentation & individual contribution 10/50 (Round 1 60% / Round 2 40% of the presentation share). The milestone weights say when marks are earned; the rubric below says how the submitted work is judged. 20 + 30 + 50 = 100% of PRJ.

Submission deadlines (all at 23:59): D1 — Sun 13 Sep · D2 — Sun 25 Oct · D3/D4 v1 — Sun 29 Nov · final D3/D4 — Fri 11 Dec. These dates follow the current timetable; later instructor or registrar announcements take priority. Late submissions: −10% per day for up to 3 days; after that, the submission receives 0.

04 · Ideas

Suggested project themes

Deliberately open — propose your own theme if you prefer, as long as it satisfies the requirements above.

01

Research assistant agent

Literature search + retrieval (RAG/GraphRAG) + cross-session memory + MCP tools (arXiv, Semantic Scholar); injection tests through retrieved papers.

02

Repository maintenance agent

Issue triage → patch proposal → sandboxed test run; planning + reflection + permission-gated tools; evaluated with pass@1/pass^k.

03

Data-analysis / BI agent

Natural-language questions → SQL/pandas via MCP over a database; schema memory; SQL-level least privilege against injection via table contents.

04

Multi-agent software team

MetaGPT/ChatDev-style team vs. a single agent on the same tasks at matched budget; failure-mode and collusion analysis.

05

Web/computer-use agent

A bounded domain (university portal, e-commerce sandbox, WebArena subset); planning + memory; safety gates on irreversible actions.

06

Customer-support agent with policies

τ-bench-style tool use under rules with escalation to a human; security against user-side social engineering and data exfiltration.

07

Secure agent gateway

A defense-focused project: an MCP proxy implementing permission control or CaMeL-style taint tracking, evaluated on AgentDojo's utility/security trade-off.

08

Long-horizon personal assistant

Episodic/semantic memory design evaluated on long-conversation benchmarks; memory-poisoning attacks and detection.

09

Agentic RAG for Vietnamese documents

Legal/administrative/university regulations; a retrieval-decision policy, grounding evaluation, hallucination analysis.

10

RL fine-tuning for tool use

GRPO / verifiable rewards on a narrow tool-use task with a small open model, compared to prompting a larger model at equal cost.

05 · Writing

Report & proposal templates

Proposal (D1, 3–4 pages)

Topic-quality self-assessment (novel / non-trivial / meaningful / feasible — see the gate above, in your own words, not left for the instructor to infer) · Title, group & roles · Problem & users · Related systems & papers (5–10 refs) · Proposed architecture (diagram, control loop, tools/MCP with permission levels, memory design, orchestration — mark your ≥ 3 axes) · Evaluation plan (task set, metrics, baselines, seeds) · Threat model v0 (assets, entry points, attacker capabilities, initial mitigations) · Work plan to W7 and W12 · Risks & fallback scope · AI-use statement.

Progress report (D2, 4–6 pages)

Delta from proposal (scope changes, with reasons) · Implemented architecture (what runs end-to-end today) · Tools/MCP and memory: implemented vs. planned · Evaluation harness with first numbers and cost so far · Threat model v1 with first injection results · Plan to W12 · AI-use statement.

Final report (D3, 6–8 pages, conference style)

Abstract · 1 Introduction · 2 Background & related work · 3 System design (architecture, reasoning/planning, tools/MCP, memory, orchestration, and design rationale) · 4 Implementation · 5 Evaluation (setup, metrics, results, ablations, cost/latency, error analysis) · 6 Security & safety analysis (threat model, attack cases and results, permission control, monitoring, residual risks) · 7 Limitations, threats to validity, extensibility · 8 Ethics & responsible-use considerations · 9 Conclusion & future work · References · Appendix: reproducibility (commands, seeds, hardware, budget), contribution statement, AI-use statement.

06 · Logistics

Compute & API policy

You may use hosted LLM APIs (course-provided credits, if available, or your own keys), local open-weight models via Ollama/vLLM, or university GPU resources where available. The proposal must state the model(s) you plan to use and an estimated budget; the final report must report actual spend.

Frameworks are your choice — LangGraph, the Anthropic/OpenAI SDKs, AutoGen, CrewAI, smolagents, or plain Python — but the report must explain what the framework does for your architecture and what you built by hand.

Non-negotiable No evaluation run without cost logging. Use local models during development; reserve API spend for the evaluation runs that go into your report.
