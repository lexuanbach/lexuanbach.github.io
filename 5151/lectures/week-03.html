Foundations: Tools, Context & Evaluation

Function calling and the Model Context Protocol at the level of what they standardize (and where they're vulnerable); context-window management; and the benchmarking methodology your project's own evaluation (Requirement R5) has to meet.

Learning objectives

By the end of this session, you can

  1. Explain how native function calling works mechanically (schema → constrained generation → execution → observation) and identify failure modes specific to irreversible or expensive tools.
  2. Describe MCP's architecture (host/client/server, the three core server primitives, and capability discovery) and explain what problem it solves that per-tool custom integrations do not.
  3. Name at least three concrete context-management techniques and the failure mode each one addresses.
  4. Design a credible evaluation for an agent system: choose a metric, justify a baseline, and specify what must be controlled for (seeds, cost, contamination) to make the result trustworthy.
  5. Defend a project proposal against exactly this methodology bar in the pitch segment of this session.
01 · Tool use and function calling

From free text to constrained action

LLMs naturally generate text, while tools require valid, typed calls. For an agent to act — call an API, run a query, execute code — the application needs a reliable bridge between those two forms. Three approaches are worth distinguishing because they make different reliability trade-offs:

  • Toolformer (Schick et al., NeurIPS 2023) — a model fine-tuned to insert tool-call tokens into its own generated text, self-supervised by checking whether the call improves its own prediction of following tokens. Tool use is baked into one model's weights — not something you can add a new tool to without retraining.
  • ToolLLM (Qin et al., ICLR 2024) — scales tool use to 16,000+ real-world APIs via instruction-tuning, plus a search procedure for tool selection when the candidate set is too large to consider by brute force. First point where "which tool, out of thousands" becomes its own sub-problem.
  • Native function calling (current commercial LLM APIs) — the provider trains the base model to reliably emit a structured call given a list of tool schemas in context, with no extra fine-tuning by the developer. What nearly every framework you'll use calls under the hood.

Native function calling, mechanically

You provide the model with a schema per tool at inference time — name, description, and a typed parameter specification:

{
  "name": "search_flights",
  "description": "Search for available flights between two cities on a given date.",
  "parameters": {
    "type": "object",
    "properties": {
      "origin": {"type": "string", "description": "IATA airport code, e.g. 'SGN'"},
      "destination": {"type": "string", "description": "IATA airport code, e.g. 'HAN'"},
      "date": {"type": "string", "description": "ISO 8601 date, e.g. '2026-09-14'"}
    },
    "required": ["origin", "destination", "date"]
  }
}

At generation time, the model either produces ordinary text or a structured call matching one of the provided schemas. The calling application validates the arguments, executes the call, and appends the result back into context as an Observation — exactly the execute(decision.action, tools) step from Lecture 1's control loop, made concrete.

Native function calling, mechanically.
Treat schemas and tool results as part of the security boundary The model chooses among tools using their names, descriptions, parameter schemas, and the surrounding instructions. Vague metadata can cause wrong selections or malformed arguments. Tool descriptions and results may also contain untrusted text that tries to redirect the model; instruction hierarchy helps, but it does not remove the need for validation, least privilege, and approval before consequential actions.

Error handling, idempotency, and irreversibility

Three properties of a tool call that must be designed for explicitly:

  • Idempotency — does calling the tool twice with the same arguments have the same effect as calling it once? A get_weather call is idempotent; a charge_card call is not. Agents retry on failure by design — a non-idempotent tool called twice by accident during a retry is a real, common failure mode.
  • Reversibility — can the effect be undone? Sending an email cannot be undone; a draft order usually can be. The ReAct critique in Lecture 2 applies here directly.
  • Error surfacing — a raw stack trace, a structured error the model can retry differently, or a silent failure that looks like a valid empty result?

For your own project (Requirement R2), each tool's permission level should record whether it is read-only, reversible-write, or irreversible-write — the first input to your threat model (Requirement R6).

Worth knowing as a pointer: the Berkeley Function-Calling Leaderboard (alongside Patil et al.'s Gorilla) measures function-calling correctness — right function, right arguments, right format — separately from whether the overall task succeeds.

02 · The Model Context Protocol

Reducing an M×N integration problem toward M+N

Before a standard protocol, every agent framework connecting to a database, a filesystem, and a ticketing system had to write custom integration code for each pairing — an M × N problem. Anthropic's Model Context Protocol (2024) reduces those pairwise integrations toward M + N: each tool or data source implements a server interface, and each application implements a client interface. Authentication, permissions, and application policy still need integration work. MCP does not make agents smarter; it makes tool integration a reusable engineering problem.

One host creates a dedicated client for each server it uses

The host is user-facing and owns the LLM conversation — and, critically, is where user consent should be enforced. The host creates one client for each server it uses; that client maintains a dedicated communication channel. A local stdio server usually serves one client, while a remote HTTP server can serve many. Each server exposes one system's capabilities without needing to know which LLM or other servers the host uses.

PrimitiveWho controls itAnalogyExample
ToolsModel-controlledA function the model can callquery_database(sql)
ResourcesApplication-controlledA file the model can readfile:///project/README.md
PromptsUser-controlledA reusable slash-command/template/summarize-ticket
ElicitationUser-controlled through the hostA server asking the user for missing information or confirmationConfirm an irreversible action

Tools, resources, and prompts are the three core primitives a server can expose. Elicitation is a client feature in the other direction: it lets a server request user input through the host. This split acknowledges that not every decision should be delegated to the model. The current protocol is stateless at the data layer and uses discovery metadata on requests; this differs from the 2024 protocol described in the launch announcement, which used an initialize handshake and included sampling. A simplified current message flow (MCP uses JSON-RPC 2.0):

tools/list is the schema-advertising step from §1, now standardized and served dynamically by the tool provider. The host discovers what the server advertises; the application can filter that list before exposing tools to the model. MCP is transport-agnostic: a local stdio server inherits the host process's own privileges directly; a remote HTTP server is a genuine network boundary you must reason about separately.

Security, previewed (covered in depth in S2-3/S2-4)
  • Tool descriptions and results can contain untrusted instructions. They do not have the same authority as the host's system instructions, but they can still manipulate model behavior if the application treats them as ordinary context.
  • Scoping and consent belong in the host, not the model. Elicitation gives a server a standard way to request confirmation, but the host still decides what to show, what to authorize, and whether an irreversible call may proceed.
  • A "confused deputy" risk: an agent with legitimate access to multiple servers can be tricked, via content from one server, into misusing its access to another — exactly Willison's "lethal trifecta" framing (S2-3): untrusted content + private data + external communication, together in one agent.

MCP vs. A2A, briefly

MCP standardizes agent-to-tool/data communication. Google's Agent2Agent (A2A) protocol (2025) instead standardizes agent-to-agent communication — a different problem (peer coordination). The two are complementary: a multi-agent system (S2-1) plausibly uses A2A between agents and MCP from each agent to its own tools.

03 · Context management

The window is finite, and position matters

Everything an agent "knows" at decision time must fit in the model's context window. Two distinct problems follow, worth keeping separate: capacity (a hard token limit) and positional degradation — even within capacity, "lost in the middle" (Liu et al., TACL 2024) shows models are empirically less accurate at using information placed in the middle of a long context than near the beginning or end.

Accuracy at retrieving a fact, by its position in a long context (illustrative shape)

This is the direct, practical reason "just put everything relevant into a giant context window" is not a substitute for the memory and retrieval design in S1-3/S1-4 — a fact being present in context is not the same as the model reliably using it.

04 · Research and benchmarking methodology

Design the evaluation before you build

This goes before Seminar 1 and before most groups have working code — deliberately: an evaluation plan designed after a system exists tends to be shaped to flatter what it already does well.

Metrics: task success, pass@k, and cost/latency together

  • Task success rate — meaningless without stating how correctness is checked; an LLM-judged "success" and a unit-test-verified "success" are different metrics wearing the same name.
  • pass@k — given k independent attempts, the fraction where at least one succeeds. Assumes you can reliably pick the successful attempt in real deployment — often the unsolved part of the problem.
  • pass^k (Yao et al., τ-bench, 2024) — given k attempts, the fraction where all k succeed. A much stricter, deployment-relevant reliability measure: a technique succeeding 90% of the time on any one attempt can still be unreliable across repeated calls.
  • Cost and latency, always reported alongside success — a technique spending 10× the tokens (self-consistency, ToT — Lecture 2) is not unconditionally "better," it's a different point on a cost-quality curve.
Illustrative — same underlying success rate, opposite trend depending on which metric you report.

Formal definitions

Both metrics are usually computed with an unbiased estimator, not a naive repeated trial — sample n attempts per task once (n ≥ k), count how many succeeded, then compute every k you care about from that same batch of samples. This avoids the high variance of literally re-running the task k times over and over, and it's cheaper: one batch of n samples yields pass@1, pass@8, and pass@100 alike.

pass@k — probability at least one of k attempts succeeds pass@k = 𝔼tasks [ 1 − C(n−c, k) / C(n, k) ]

For one task: sample n attempts, of which c succeed. C(n, k) is "n choose k" — the number of ways to pick k of the n samples. C(n−c, k) / C(n, k) is the probability that a randomly chosen set of k samples contains zero successes (all k drawn from the n−c failures); subtracting from 1 gives the probability at least one succeeds. Average over tasks. (Chen et al., 2021 — the Codex paper that introduced this estimator.)

pass^k — probability ALL k attempts succeed pass^k = 𝔼tasks [ C(c, k) / C(n, k) ]

Same n samples and c successes per task, but now the numerator is the number of ways to pick k samples that are all successes — the probability a random k-subset is entirely successful. Structurally the mirror image of pass@k (successes and failures swap roles), and much stricter: a task with 90% single-attempt success can still have a low pass^8 if that 10% failure rate is spread independently across attempts. (Yao et al., τ-bench, 2024.)

Reporting variance across seeds (Requirement R5) p̄ = (1/m) Σᵢ pᵢ  SE = s / √m

Run m ≥ 3 independent seeds, each giving a success rate pᵢ. Report the mean p̄ and the standard error SE (sample standard deviation s divided by √m) — a single number with no spread reported is a point estimate dressed up as a result. If two configurations' means are within a standard error or two of each other, the comparison is not decisive evidence of a real difference.

Seeds, ablations, contamination, and LLM-as-judge

  • Seeds/variance — a single run's success rate is a point estimate with unknown variance. Requirement R5 asks for at least 3 independent runs so you can show run-to-run variation; small effects may require more runs or confidence intervals.
  • Ablations — isolate one variable (same system, module removed) — not a comparison against an unrelated baseline that also differs in other ways.
  • Contamination — public benchmarks may already be in a model's pretraining data, inflating performance for reasons unrelated to the technique.
  • LLM-as-judge — documented biases (verbosity, style-similarity, order sensitivity). If you use one, state which model, what prompt, and ideally validate against a small human-labeled sample.

Reproducibility packaging

A result nobody else can reproduce is not yet a result the field can build on (Requirement R8): pin dependency versions, record seeds, log the exact model version/date used, and provide a one-command path from a clean checkout to the reported numbers.

Requirement R5, made concrete A task set of ≥ 20 instances from a defined source · at least one success metric with cost and latency reported alongside it · ≥ 2 system configurations compared (your ablation) · ≥ 3 independent runs/seeds with variance shown · an error analysis categorizing why failures happened (wrong tool call, context overflow, hallucinated fact, evaluator too strict/lenient) — usually the most informative part of an evaluation and the part most often skipped.
05 · Discussion questions

For this session

  1. For a tool your project will expose: is it read-only, reversible-write, or irreversible-write? What changes in your architecture if you got that classification wrong?
  2. MCP's three-way split of tools/resources/prompts by who controls them — pick one primitive and describe a scenario where using the wrong one creates a security or usability problem.
  3. "Lost in the middle" suggests position matters independently of capacity. Would you expect a shorter context with critical facts near the end to outperform a longer context with the same facts buried in the middle? What would make you wrong?
  4. Pick one paper you've read so far this semester and identify which of pass@1 / pass@k / pass^k it reports (or should have reported) — does the choice match the claim being made?
Takeaway

If you remember nothing else from today

A tool call, a context window, and an evaluation number are all the same kind of claim: they look solid until you check what they're silently assuming. A tool's description is untrusted input, not documentation. A longer context is not evenly usable context. And a single accuracy number with no cost, no variance, and no pass^k is not evidence — it's a demo. Your own project's R2/R5/R6 requirements exist because each of these failure modes is real and common, not because the rubric needed more rows.

4. What does pass^k measure that pass@k does not?

Code exercise. This function is supposed to implement the pass@k unbiased estimator from §04 — but for a task with c = 0 successes out of n samples, it should always return 0.0, and it doesn't. Find the bug.

from math import comb

def pass_at_k(n, c, k):
    # n = samples drawn, c = how many succeeded, k = attempts we care about
    # TODO: bug -- returns the WRONG value (try c=0 and see)
    return comb(n - c, k) / comb(n, k)
Show solution

The function is missing the 1 − in front. comb(n − c, k) / comb(n, k) is the probability that a random k-subset contains zero successes — for c = 0 that's the probability of drawing k zeros from an all-zero set, which is 1.0, not 0.0. Subtracting from 1 flips it to "at least one success," which is what pass@k actually means.

def pass_at_k(n, c, k):
    return 1 - comb(n - c, k) / comb(n, k)
