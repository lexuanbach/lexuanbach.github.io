Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks

The paper that made "look it up, then answer" part of generation itself, not a separate pipeline stage bolted on afterward — and the direct ancestor of nearly every agent's semantic-memory design.

Read the paper ↗ Lewis et al. (Facebook AI Research) · NeurIPS 2020 ← Back to Tools, MCP & Evaluation
01 · In plain terms

A model's memorized knowledge is frozen the day training ends

An LLM's parametric knowledge — whatever it absorbed during training — cannot change without retraining it, and it was never designed to hold every fact reliably or keep facts up to date. Retrieval-Augmented Generation's fix is to give the model an open book: before generating an answer, search an external corpus for the handful of passages most relevant to the question, and condition generation on those passages directly. The model doesn't have to have memorized the fact — it just has to read it off the page it was just handed, the same way a person answers better with a reference book open in front of them than from memory alone.

02 · How it works

A dense retriever and a generator, trained together

Two components, trained jointly end-to-end: a retriever — a dense passage-retrieval model that encodes the query and every candidate passage into the same embedding space with two separate encoders (a "bi-encoder"), so relevance becomes a simple vector similarity search — and a generator (the original paper used BART-large) that conditions its output on the query concatenated with whichever passages the retriever returned. Because the corpus can be millions of passages, the retriever's nearest-neighbor search runs against a pre-built approximate index (FAISS in the original paper, over 21 million Wikipedia passages) rather than comparing against every passage individually. Two variants differ in exactly where the retrieved passages enter the picture: RAG-Sequence picks one set of passages for the whole generated answer, while RAG-Token lets the model draw on a different passage for each output token.

The key design choice worth naming in any critique: retrieval happens once, up front, before generation starts — this is exactly the limitation Week 3's evaluation section and Self-RAG / FLARE (cited alongside this paper in the seminar reading list) were built to address, by making retrieval conditional on the model's own uncertainty rather than a fixed step.

RAG's retrieve-then-generate pipeline. Lewis et al., NeurIPS 2020.
Key result The original RAG model (BART-large generator + a dense retriever indexed over 21M Wikipedia passages) reached 44.5 Exact Match on Natural Questions, outperforming comparable parametric-only language models on open-domain question answering.

The fuller picture: an offline index and an online query, sharing one embedding space

The four-box pipeline above compresses two things that actually run at very different times. Offline, once, before any user ever asks a question: every passage in the corpus is encoded into a vector and dropped into a nearest-neighbor index. Online, on every query: the query is encoded into that same embedding space — the query and passage encoders are trained together as a pair, which is what makes comparing them meaningful — and the index is searched for the closest passage vectors, which the generator then conditions on.

RAG's full architecture: the offline path builds a vector index over the corpus once; the online path encodes each query into that same space, searches the index, and conditions generation on the result.
Worked exampleGrounding a question the model alone might get wrong

Q: "What's the capital of the country that won the 2022 FIFA World Cup?"

Parametric onlyThe model may answer from training-time memory alone — reliable only if it was trained after the event and recalls it correctly. RAG retrievesPassage 1: "Argentina won the 2022 FIFA World Cup, defeating France on penalties." Passage 2: "Buenos Aires is the capital and largest city of Argentina." GeneratorConditions on both passages directly — the answer ("Buenos Aires") is now grounded in retrieved text, not recalled from memory.
04 · For your talk & project

What this buys you

  • If you present S1-4 Retrieval-Augmented & Knowledge-grounded Agents: this is the paper every later technique in that topic modifies — GraphRAG changes what gets indexed, Self-RAG and FLARE change when retrieval happens. State explicitly what each later paper changes relative to this fixed pipeline.
  • For your project's memory design (R3): if your semantic memory is a vector store you query before generating, you are building a RAG system whether or not you use that name — cite this paper as the mechanism's origin and be ready to say which variant (retrieve once vs. conditionally) you implemented.
  • A sharp critical question: what happens to answer quality when the retriever returns confidently-ranked but irrelevant passages — does your system have any check before trusting them?
