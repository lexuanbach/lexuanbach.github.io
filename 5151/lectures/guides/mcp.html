Paper Guide · Week 3 — Tools, MCP & Evaluation

Introducing the Model Context Protocol

An open standard for how an AI application talks to the tools and data sources around it — replacing one custom integration per (application, tool) pair with one protocol every pair can share.

Read the paper ↗ Anthropic · November 2024 ← Back to Tools, MCP & Evaluation
01 · In plain terms

USB-C for AI tool connections, roughly

Before MCP, if you wanted your AI application to read files, query a database, and search the web, you wrote three separate custom integrations — and if you had five applications each needing those same three capabilities, that's fifteen integrations, all slightly different. MCP replaces the M × N problem (M applications × N tools) with an M + N one: any application that speaks MCP as a client can talk to any tool that exposes itself as an MCP server, with no bespoke glue code per pair. The protocol itself is not novel cryptography or a new wire format — it's JSON-RPC 2.0, a decades-old standard — the actual contribution is agreeing on what gets exchanged: a small, fixed vocabulary of primitives every server and client understands the same way.

02 · How it works

One server, four primitives

Every MCP server exposes some combination of three server primitives: Tools (functions the model can call, with sanctioned side effects — send an email, run a query), Resources (read-only context addressable by URI — a file, a database row, a log), and Prompts (parameterized templates a user can invoke directly, often surfaced as slash commands). There is one client primitive in the other direction, Sampling: a server can ask the host's own LLM for a completion, useful when a server needs a small piece of reasoning without embedding its own model. A host application (the thing the user interacts with — Claude Desktop, an IDE, a custom agent) embeds one MCP client per server connection; each client keeps one stateful 1:1 session, opened with an initialize handshake, over either stdio (a local subprocess) or HTTP (a remote server).

A critical point for any security analysis (this course's R6): every Tool description and every Resource's content is untrusted input from the model's perspective, exactly like a webpage a browser renders — a malicious or compromised server can return content engineered to manipulate the model, which is why permission control and least-privilege tool access matter as much as the protocol's own correctness.

One MCP server's four primitives — three flow server→host, Sampling flows the other way. Anthropic, 2024.

04 · For your talk & project

What this buys you

  • If you present S1-2 Tool Use & MCP: the M×N → M+N argument is the single sentence that justifies the whole protocol's existence — lead with it, then show the four primitives as what actually got standardized.
  • For your project's tool integration (R2): using an existing MCP server (or writing a minimal one — Tools + one Resource is often enough) satisfies this requirement more convincingly than an ad-hoc function-calling setup, and gives you a natural place to add permission checks for R6.
  • Compare against Google's A2A protocol in Q&A if asked: MCP is agent-to-tool, A2A is agent-to-agent — complementary, not competing standards.
