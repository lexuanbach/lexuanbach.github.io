Lost in the Middle: How Language Models Use Long Contexts

A bigger context window is not the same as uniformly usable context — this paper measured exactly how much worse a model is at using information buried in the middle, across six different model families.

Read the paper ↗ Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni & Liang · TACL 2024 (arXiv 2023) ← Back to Tools, MCP & Evaluation
01 · In plain terms

"It fits in the context window" is not the same as "the model will use it"

Context windows kept growing, and it was tempting to assume a model uses a 20,000-token context the same way regardless of where in it the important fact sits. This paper tested that assumption directly, with a simple, almost embarrassingly direct method: put the one document that actually answers the question at different positions inside a long context, keep everything else the same, and measure whether the model still gets the answer right. The result is a clean, repeatable U-shape — strong at the very start of the context, strong at the very end, and measurably worse in the middle. This is not one model's quirk; it showed up across every model family the paper tested.

02 · How it works

Multi-document QA, with the answer's position as the only variable

The core experiment: assemble a context containing about 20 documents, exactly one of which contains the answer to a given question (the rest are plausible-looking distractors). Hold the question and the documents themselves fixed, and vary only where the answer-bearing document sits — position 1, 5, 10, 15, or 20 out of 20. Everything else about the task is identical across runs, which is what makes the position effect isolable rather than confounded with task difficulty. The paper reran the same logic with a synthetic key-value retrieval task (find the value for a given key among many key-value pairs) specifically to rule out "maybe it's just that QA is hard" as the explanation — the same U-shape showed up there too, which points to something about how these models process position generally, not an artifact of one task format.

Six model families were tested: GPT-3.5-Turbo, GPT-4, Claude 1.3, LongChat-13B, MPT-30B, and Cohere Command — the U-shape held across all of them, though its depth varied by model.

Illustrative reconstruction of the U-shape (exact values vary by model). Liu et al., TACL 2024.
Key result Accuracy dropped by 20–30 points when the answer-bearing document sat in the middle positions (10/15 of 20) compared to position 1 or 20 — a gap observed across all six model families tested, including GPT-4 and Claude.
Worked exampleA support agent's context, laid out badly
System prompt15 company policy documents concatenated in alphabetical order: Billing, Cancellations, Data-retention, … Refunds (8th), Warranty. User asks"Can I get a refund for this order?" RiskThe Refunds policy sits at position 8 of 15 — squarely in the "lost" zone this paper measured — so the agent may answer from a vaguer general impression rather than the specific policy's actual terms. FixRetrieve and re-rank so the most relevant document for this query is placed first (or last), rather than relying on a fixed, alphabetical context order.
04 · For your talk & project

What this buys you

  • If you present S1-3 Agent Memory: this is the citation for why "just put everything in the context window" is not a neutral design choice — pair it directly with MemGPT's paging mechanism as the two-sided argument (why context management is needed, and one concrete way to do it).
  • For your project's memory design (R3) and evaluation (R5): if your agent concatenates retrieved passages or conversation history into a long prompt, this paper is direct evidence you should test accuracy as a function of where the critical information ends up — not just assume more context is strictly better.
  • A sharp critical question for any RAG or long-context demo: did you test what happens when the correct passage is retrieved but placed in the middle of several others?
