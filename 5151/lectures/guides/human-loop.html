Human-in-the-Loop vs. Human-on-the-Loop

The autonomy spectrum from earlier in this lecture describes what a system can do. This is the design question that follows immediately: who has to sign off before it does it, and how often?

Read the paper ↗ Shavit, Agarwal et al. (OpenAI) · 2023 ← Back to Introduction & Methodology
01 · In plain terms

Approve every step, or watch the dashboard?

Human-in-the-loop (HITL) means no action executes without a human approving it first — a checkpoint before every single step. Human-on-the-loop (HOTL) means the agent acts on its own between check-ins; a human monitors status and can intervene, but isn't asked to approve each individual action. The difference isn't how capable the agent is — it's how the surrounding system is wired. The same ReAct-style agent can be deployed either way; HITL and HOTL are deployment decisions layered on top of the agent's own autonomy level (§01 above), not properties of the agent itself.

Push HOTL far enough — no check-ins at all, indefinite unsupervised operation — and you get a third point some literature names explicitly: human-out-of-the-loop. This course's autonomy spectrum's Level 5 ("open-ended," only intermittent human oversight) sits right at that edge.

02 · How it works

Where the spectrum forces the choice

Levels 0–2 of the autonomy spectrum are HITL by construction: a single call or a hand-authored workflow already has a human (the developer) approving every step, just at design time rather than run time. The real design decision only appears at Level 3, where the model starts choosing its own steps — this is exactly where a team has to decide whether every action still gets a human gate, or whether the agent runs autonomously with periodic oversight instead. Shavit et al.'s practical answer, concretely: don't leave that choice implicit. Build actual mechanisms for it —

  • Approval gates for HITL: specific action types (irreversible, costly, or high-stakes ones) are hard-blocked until a human explicitly approves, regardless of how confident the agent is.
  • Periodic reauthorization for HOTL: the agent is made to "time out" automatically after N actions or T minutes, requiring a human to review and explicitly reauthorize before it can continue — not waiting for something to visibly go wrong first.

The trade-off is the same one Week 1's autonomy table already names: HITL caps how much work the system can get through (a human reviews every step), while HOTL trades some of that certainty for throughput — and inherits the risk that whatever happens between check-ins goes unsupervised.

Same underlying agent loop — HITL gates every step; HOTL checks in periodically.
Worked exampleThe same coding agent, deployed two ways

A ReAct-style coding agent that can read files, write code, and run git commit:

HITL deploymentEvery file write and every commit is shown to the developer as a diff; nothing lands until they click approve. Slow, but nothing ships unreviewed. HOTL deploymentThe agent reads, writes, and commits freely to a feature branch for up to 30 minutes or 20 commits, then pauses and pings the developer with a summary to review before it's allowed to continue or open a PR. The failure each invitesHITL: developer approval fatigue — rubber-stamping diffs without really reading them. HOTL: a 30-minute window is enough time for a bad early decision to compound into a much bigger mess before anyone looks.
04 · For your talk & project

What this buys you

  • If you present S2-5 Safety & Alignment or S2-8 Production, Governance & Ethics: this HITL/HOTL distinction is the operational layer underneath abstract "alignment" or "oversight" language — name which mechanism a paper actually implements, not just that it claims "human oversight."
  • For your project's security analysis (R6): state explicitly which of your agent's action types are HITL-gated (and why those specifically) versus which run under HOTL — an undifferentiated "a human can review the logs" is not a design, it's an absence of one.
  • A sharp critical question for any agent demo: what's the largest amount of unsupervised action your design allows between one human check-in and the next, and what's the worst thing that could happen inside that window?
