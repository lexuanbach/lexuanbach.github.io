CoALA: Cognitive Architectures for Language Agents

A vocabulary for talking about any agent's design: what it remembers, what it can do, and how it decides — the framework Week 1's anatomy diagram and every seminar topic's memory/tool sections are built on.

Read the paper ↗ Sumers, Yao, Narasimhan & Griffiths · TMLR 2024 ← Back to Introduction & Methodology
01 · In plain terms

An agent is memory plus a decision loop, not a bigger prompt

Before CoALA, "agent" papers each invented their own vocabulary — one called its scratchpad a "buffer," another called the same thing a "trace." Sumers et al. borrowed a much older vocabulary from cognitive science (Tulving's memory taxonomy, used to describe human memory since the 1970s) and applied it to language agents. The claim is simple: every agent, however it's built, can be described as (1) a set of memory modules holding different kinds of information, (2) an action space of things it can do, and (3) a decision procedure that reads memory and picks the next action. This guide exists because Week 1's whole "anatomy of an agent" section (LLM · memory · tools · environment) is CoALA's vocabulary in different words — knowing the original taxonomy makes every later seminar topic on memory (S1-3) and orchestration (S1-7) click faster.

02 · How it works

Four memories, one loop

The four memory modules — working memory holds whatever is active right now (the current prompt, intermediate results); it resets often. The other three are long-term: episodic memory is a record of the agent's own past experience ("last time I tried X, it failed because Y"); semantic memory is general facts and world knowledge (a knowledge base or vector store of documents); procedural memory is skills — for an LLM agent, this is mostly the model's own weights, plus any code/tools it has learned to call reliably. Splitting memory this way matters because each kind fails differently and needs a different fix: a working-memory problem is a context-window problem (§ Week 3's "lost in the middle"); an episodic-memory problem is "the agent keeps repeating the same mistake."

The action space splits into internal actions (reasoning, retrieving from memory, writing to memory — nothing leaves the model) and external actions (grounding: calling a tool, sending a message, acting in an environment — this is where MCP, Week 3's topic, lives). The decision procedure is the loop that ties it together: propose one or more candidate actions, evaluate them (often just "pick the first one," sometimes a real search as in Tree of Thoughts), and select one to execute. That propose→evaluate→select cycle, repeated, is the agent loop from Week 1's simulator.

CoALA's memory + action-space + decision-procedure framework. Sumers et al., TMLR 2024.
Worked exampleMapping a customer-support agent onto CoALA

Take a support agent that answers billing questions. In CoALA's vocabulary:

WorkingThe current ticket text and the last 2 turns of conversation. EpisodicA log of past tickets this agent resolved, retrievable by similarity ("a customer asked this exact refund question 3 weeks ago"). SemanticThe company's refund policy documents, indexed for retrieval (this is what a RAG pipeline, S1-4, fills). ProceduralThe base model's own trained ability to write a polite, on-policy reply — no separate module, just weights. Internal actionRetrieve the refund policy clause that applies to this ticket. External actionCall issue_refund(amount, order_id) — an MCP tool with real financial consequences.

This is the exact exercise Week 1's "memory, made concrete" section repeats for a coding assistant and a research assistant — CoALA is why those three examples all use the same four labels.

04 · For your talk & project

What this buys you

  • If you present S1-3 Agent Memory: open with CoALA's taxonomy, then show how MemGPT, Generative Agents, and A-MEM each specialize one part of it (MemGPT ≈ engineering working memory's overflow; Generative Agents ≈ a retrieval-scored episodic store) — this gives your audience one map to place every paper on, exactly what the "must explain" checklist for that topic asks for.
  • For your project proposal (R3 memory requirement): naming your design in CoALA's terms ("we use working memory for X, episodic for Y, no semantic store") is a fast, legible way to satisfy the "explicit design" bar the rubric checks for.
  • A sharp critical question to raise in Q&A on any memory paper: "which of the four modules does this actually implement, and which does it just assume away?"
