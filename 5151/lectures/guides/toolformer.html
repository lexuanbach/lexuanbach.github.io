Toolformer: Language Models Can Teach Themselves to Use Tools

Before every commercial LLM API offered native function calling, this paper asked: can a model teach itself which API to call, when, and with what arguments — using its own prediction quality as the only supervision signal?

Read the paper ↗ Schick, Dwivedi-Yu, Dessì, Raileanu, Lomeli, Zettlemoyer, Cancedda & Scialom · NeurIPS 2023 ← Back to Tools, MCP & Evaluation
01 · In plain terms

The model grades its own guesses about when a tool would help

Toolformer's trick is self-supervision with no human-labeled examples of "when to call a tool." Take a large corpus of plain text, and at many candidate positions, have the model propose an API call it thinks might help predict what comes next (a calculator call before a number, a search-engine call before a fact). Actually execute each candidate call, insert its result into the text, and check: does having that result measurably improve the model's own prediction of the following tokens, compared to not having it? Keep only the calls that pass this test, throw away the rest, and fine-tune the model on the resulting (call-augmented) text. The model ends up having taught itself tool use from its own self-graded experiments — no human ever labeled a single example.

02 · How it works

Sample, execute, filter by perplexity, fine-tune

Concretely: (1) prompt the base model with a few in-context examples of each tool's API format, and sample candidate calls at many text positions across a large corpus; (2) execute every candidate call against the real tool (a calculator, a Q&A system, two search engines, a machine-translation system, a calendar — five tools total in the original paper); (3) for each candidate, compare the model's cross-entropy loss on the tokens that follow, with versus without the call's result inserted — keep the call only if it reduces loss beyond a threshold; (4) fine-tune the base model on the resulting filtered dataset, so the model learns to emit API(query) tokens at the right positions unprompted, at inference time.

The key limitation to know cold: because tool use is baked into the fine-tuned weights, adding a new tool means running this entire pipeline again and re-fine-tuning — you cannot hand a deployed Toolformer model a new API description and expect it to use it. That single limitation is the reason the field moved toward native function calling (a schema passed at inference time, no fine-tuning needed) within about a year.

Toolformer's self-supervised training pipeline. Schick et al., NeurIPS 2023.
Key result With five tools (calculator, Q&A, two search engines, translation, calendar) and zero human-labeled call examples, Toolformer achieved substantially improved zero-shot performance on question-answering and math tasks — often competitive with much larger models — without hurting its core language-modeling ability.

04 · For your talk & project

What this buys you

  • If you present S1-2 Tool Use & MCP: open with this paper precisely to set up the contrast with native function calling and MCP — "baked into weights" versus "passed as a schema at inference time" is the single most important distinction in this topic's technical history.
  • For your project's tool integration (R2): you will almost certainly use native function calling or MCP, not Toolformer's fine-tuning approach — be ready to explain in Q&A why that's the right choice for a 10-week project (no training infrastructure needed, tools addable without retraining).
  • A sharp critical question: Toolformer's filtering keeps calls that reduce loss on the next few tokens — does that really guarantee the call was useful for getting a correct final answer several steps later?
