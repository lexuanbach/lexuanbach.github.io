Learning objectives

By the end of this session, you can

  1. Define an "agent" precisely enough to distinguish it from a chatbot, a workflow, and a script, and place a given system on an autonomy spectrum.
  2. Decompose any agentic system into four functional components — perception/context, reasoning, memory, action/tools — wired together by a control loop, and map each seminar topic in the course onto this anatomy.
  3. Apply a three-pass method to read a research paper, and reproduce the five-part structure every seminar talk must follow.
  4. Ask an assumption-level critical question about a paper's claims, rather than a summary-level comprehension question.
01 · From LLMs to autonomous agents

A working definition, and an autonomy spectrum

"Agent" is used loosely enough in industry marketing that, for a research course, it needs a working definition or critique becomes impossible — there is no claim to hold a system to.

Working definition An agent is a system in which a language model's output determines the next action taken in an environment, and that action's result is fed back into the model's context before the next decision. The defining property is the loop — perceive, decide, act, observe, repeat — not any particular level of capability.

Six points on the spectrum this definition spans, from least to most autonomous. When you read a paper (or design your project), decide which level its system actually operates at — many papers use the word "agent" for level-1 or level-2 systems, and the gap between the claimed and actual level is often the paper's weakest point.

L0–L2: the developer is in the loop every call or at design time. L3–L5 (highlighted): the model decides, per task.

Anthropic's distinction (previewed here, covered in S1-7) Workflows (level 2) are predictable for well-defined tasks; agents (level 3+) trade predictability for flexibility at scale. "Find the simplest solution possible, and only increase complexity when needed" — keep this in mind when you scope your project's architecture.
02 · A short research timeline

2022 → 2026, in three phases

Orientation, not exam material — a map of where this semester's topics sit in time. Notice the shape: 2022–2023 is dominated by prompting tricks that elicit behavior from a frozen model (CoT, ReAct, Reflexion all work on off-the-shelf models). 2024 is dominated by infrastructure — protocols and benchmarks that make agents buildable and measurable at scale. 2025 is dominated by training and architecture — RL that bakes behavior into the model rather than eliciting it, and security that constrains what an agent can do rather than filtering what it's told.

03 · Anatomy of an agent

Four components, one loop

Every system covered this semester — regardless of how it's marketed — can be described with four components and one loop connecting them. This is a compressed version of Sumers et al.'s CoALA (Cognitive Architectures for Language Agents, TMLR 2024) framework.

The anatomy of an agent

Memory, made concrete: three real apps

"Memory" in the diagram above is easy to leave abstract. Three examples of what it actually looks like inside a running application — notice each uses a different kind of memory for a different reason:

Same "memory" box in the diagram above, three different write/retrieval policies.
  • A coding assistant remembers your project's conventions. Mid-session, nothing needs to persist beyond the current context window — but across a long refactor, the agent writes "this codebase uses 4-space indentation and snake_case" to a scratch file once, instead of re-deriving it (and risking a different answer) on every turn. This is short-term, working memory — cheap, session-scoped, and the kind context-window management (Lecture 3, taught in Real Week 2) is designed around.
  • A customer-support agent remembers your last three tickets. When you message again next month, the agent retrieves your ticket history from a database before responding — it does not re-read the entire company knowledge base, and it does not forget you the moment the session ends. This is long-term, episodic memory: specific past events, retrieved by relevance (MemGPT and Generative Agents' retrieval scoring, S1-3).
  • A research assistant remembers a fact it already looked up. If it searched "who won the 2023 Nobel Prize in Physics" three questions ago, a well-designed agent writes that fact to memory once and reuses it, rather than paying for the same search-and-reasoning cost again. This is semantic memory — general facts abstracted away from the specific conversation that produced them, distinct from the episodic "what happened" memory above.

The common thread: memory is a deliberate write policy (what gets saved, and when) plus a retrieval policy (what gets pulled back into context, and when) — not just "a bigger context window." Getting either policy wrong is exactly how memory becomes a liability instead of an asset: write the wrong thing and it's stale or misleading later; retrieve the wrong thing and "lost in the middle" (S1-3) means it may not even get used. S1-3 covers the write/retrieval policy design space in depth; S2-4 covers what happens when an attacker controls what gets written.

In pseudocode, almost every agent in the literature is a variant of the loop below. What differs between ReAct, Reflexion, Tree-of-Thoughts, and a multi-agent system is what happens inside this loop — not whether the loop exists.

def agent_loop(task, tools, memory, max_steps):
    context = build_initial_context(task, memory)
    for step in range(max_steps):
        decision = llm(context)                     # REASONING
        if decision.is_final_answer:
            return decision.answer
        result = execute(decision.action, tools)     # ACTION -> ENVIRONMENT
        memory.maybe_write(step, decision, result)   # MEMORY
        context = update_context(context, decision, result)  # next PERCEPTION
    return fail("max steps exceeded")

    04 · How to read, present, and critique a paper

    Three passes, five parts, six critique lenses

    The three-pass method

    Each pass costs more time and reaches deeper — most papers only need Pass 1 or 2.

    Pass 1 (5–10 min) — title, abstract, headings, figures, conclusion. After this you should be able to state the problem and the one-sentence contribution.

    Pass 2 (30–60 min) — read in order, skip proofs/derivations, treat figures as primary evidence. Note the baseline, the metric, and what experimental knobs are varied. Sketch the method from memory afterward — if you can't, you've understood the marketing, not the mechanism.

    Pass 3 (core papers only) — reconstruct the method, or run the released code. This is where you find the gap between what a paper says and what it does.

    Presentation structure (every seminar talk, no exceptions)

    1. Context & problem — why this matters, what question the papers answer.
    2. Survey of main approaches — the mechanism, not just the name.
    3. Critical analysis — 25% of your seminar grade; see below.
    4. Demo / example — a worked trace or live demo makes an abstract claim checkable.
    5. Relation to projects & open directions — a specific, falsifiable open question.

    What counts as critical analysis, versus summary

    A summary answers "what does the paper say?" Analysis answers one of these instead:

    • Assumptions — what must be true about the environment/task/model that isn't stated as a limitation?
    • Baseline validity — is the comparison fair at matched compute/cost?
    • Metric validity — does the reported number measure the actual claim?
    • Generalization — would this hold on a different model family or a harder task?
    • Reproducibility & contamination — seeds/variance reported? Is the test data plausibly in the training set?
    • Comparison across papers — do two papers in the same topic sheet implicitly conflict?
    A habit worth keeping For every core paper, write one sentence starting with "This paper's result would not hold if…" — that sentence is usually most of a critical-analysis slide.
    05 · Worked example

    A live critique of ReAct, modeled for you

    The four lenses applied below — hover each for the one-line version, full analysis in the cards.
    Worked example Yao et al. — ReAct: Synergizing Reasoning and Acting in Language Models (ICLR 2023)

    Claim. Interleaving reasoning traces ("thoughts") with actions and observations improves task success over reasoning-only (CoT) or acting-only baselines on knowledge-intensive QA and interactive decision-making tasks.

    Mechanism, reconstructed. At each step the model generates a Thought (free text), then an Action (a tool call from a fixed set), receives an Observation (the tool's result appended to context), and repeats. The thought is never executed — it exists only to condition the next action on an explicit intermediate reasoning step:

    Thought 1I need to find out who directed the film that won Best Picture in 2023. Action 1Search["2023 Best Picture Oscar winner"] Observation 1"Everything Everywhere All at Once" won Best Picture at the 95th Academy Awards. Thought 2Now I need to find the director(s) of that film. Action 2Search["Everything Everywhere All at Once director"] Observation 2Directed by Daniel Kwan and Daniel Scheinert. Thought 3I have the answer. Action 3Finish["Daniel Kwan and Daniel Scheinert"]

    This is precisely the control loop from §3 above, with decision split into an explicit Thought (why) and Action (what) pair.

    Assumption check

    Actions are assumed cheap and fast (a search API call). What happens if actions are expensive (a paid transaction) or slow (a multi-minute simulation)? The paper doesn't test this — name it as an open assumption, not a settled result.

    Baseline check

    Compared against CoT-only and Act-only at roughly matched few-shot exemplars — fair — but not against a "retrieve-then-answer" pipeline at matched token budget, which later work suggests can be competitive on some of the same benchmarks.

    Generalization check

    Results are reported on benchmarks (HotpotQA, FEVER, ALFWorld, WebShop) with action spaces designed for those benchmarks. Whether interleaving still helps with today's much stronger base models — which already reason step-by-step unprompted — is untested.

    Where does the gain come from?

    The paper's own ablations show acting-only and reasoning-only both underperform the combination — a genuine structural claim, not just a compute-budget artifact. Demand this same ablation for every technique this semester.

    Verdict for this semester

    ReAct is the ancestor of nearly every agent framework in S1-2 and S1-7 — the Thought → Action → Observation loop is what most agent SDKs, and your own project's control loop, will implement. Treat its specific empirical numbers as dated and its action-cost assumption as the thing to test, not accept, in your own systems.

    Takeaway

    If you remember nothing else from today

    An agent is defined by a loop, not a capability level — perceive, decide, act, observe, repeat. Every technique this semester (ReAct, Reflexion, multi-agent systems, RL-trained reasoning) is a variant of the same four-component anatomy: what differs is what happens inside the loop, not whether the loop exists. And critique beats summary: a paper's claim is only as strong as its weakest untested assumption — "this paper's result would not hold if…" is the sentence to keep asking, starting with your own project's design.
